# 0002. Supabase Schema and Access Rules

**Date**: 2026-10-22
**Status**: Proposed

## Summary

This decision defines the first Supabase tables and the rules that limit who can read and write them. Member identity comes from Clerk, and the database compares each row with the signed token subject. Development kiosk inserts use a separate Supabase Auth account, while production scans must pass through a trusted verifier.

## Context

K-Fit uses Clerk for member sign in and Supabase for relational data. Clerk user identifiers are text values, so they cannot be stored in PostgreSQL UUID columns or compared with `auth.uid()`. The Supabase integration must instead use the signed JWT `sub` claim as text.

The data stores user roles, two independent access flags, and attendance history. A kiosk needs a development path for testing, but an email claim by itself cannot prove that a scanned TOTP is valid or unused. Production attendance therefore requires a trusted verifier, and direct table insertion must not be granted to production Clerk tokens.

## Requirements

**User stories**:
1. As a member, I want to read only my own profile, subscription, and attendance data so that other members cannot access my information.
2. As a kiosk operator, I want development scans to be recorded only for members with both access flags active so that the test flow follows the access rules.
3. As an administrator, I want trusted backend code to provision user and subscription records without allowing a mobile client to assign privileged roles or alter subscription state.

**Acceptance criteria**:
1. **AC-1**: The migration creates `users`, `subscriptions`, and `attendance_logs` with the fields, types, defaults, keys, and constraints in the data model below.
2. **AC-2**: Each authenticated Clerk request can read only rows owned by the JWT `sub` value in `users`, `subscriptions`, and `attendance_logs`.
3. **AC-3**: Authenticated mobile clients cannot insert or change user roles or subscription state. Trusted backend provisioning is responsible for those writes.
4. **AC-4**: Direct attendance inserts are allowed only for the development Supabase Auth scanner identity, with the expected email claim and a Supabase Auth issuer, and only when both subscription flags are active.
5. **AC-5**: Production Clerk kiosk tokens cannot insert attendance directly. Production scans must be validated by trusted server code before an attendance row is written.
6. **AC-6**: Attendance IDs and timestamps are generated by the database, and attendance history cannot be removed through cascading user deletion.
7. **AC-7**: Queries for another member's rows and unauthorized attendance inserts are denied by database permissions and row level security.

## Options considered

### Option 1: Use UUID keys and `auth.uid()`

Store the member identity as a UUID and compare it with Supabase's authenticated user ID.

**Pros**:
1. Uses PostgreSQL UUID keys and the standard Supabase ownership helper.

**Cons**:
1. Standard Clerk user IDs are text values such as `user_...`, not UUIDs.
2. It would require a second identity mapping and could break the Clerk to Supabase ownership check.

### Option 2: Use Clerk subject text and row level security

Store the Clerk JWT subject as text, compare it with `auth.jwt()->>'sub'`, and use Supabase row level security to scope table access.

**Pros**:
1. Uses Clerk as the member identity provider without a duplicate identity mapping.
2. Keeps member data access checks in the database.

**Cons**:
1. Trusted server code is needed to provision user and subscription rows.
2. Kiosk identity and production scan verification need separate, explicit rules.

### Option 3: Use Supabase Auth as the canonical identity provider

Move member identities to Supabase Auth and map Clerk accounts to Supabase user IDs.

**Pros**:
1. Uses Supabase's native UUID identity and ownership helpers.

**Cons**:
1. Adds a second account mapping and synchronization path while Clerk is already the app's identity provider.

## Decision

**Chosen option**: Option 2: Use Clerk subject text and row level security.

Use text for Clerk IDs and their foreign keys. Members use signed Clerk tokens for their Supabase requests. A development Supabase Auth scanner can insert attendance only when the scanner email and native Supabase Auth issuer claims match, and the member has both access flags active. Production Clerk kiosk tokens cannot insert attendance directly.

## Rationale

The project already uses Clerk, and the Clerk to Supabase integration supplies the Clerk user identifier in the JWT subject. Keeping that subject as text avoids a second identity mapping and lets database policies compare ownership directly.

The development scanner policy is intentionally narrower than the production path. An email claim identifies a scanner account, but it does not validate a TOTP or prevent replay. Production scans must use trusted verifier code before attendance is recorded.

## Feature design

**Data model sketch**:

| Entity | Fields and constraints |
|---|---|
| `users` | `id text` primary key containing the Clerk JWT `sub`; `role text` required, defaults to `member`, and permits only `member`, `coach`, or `admin`; `created_at timestamptz` required, defaults to `now()` |
| `subscriptions` | `id uuid` primary key, generated by the database; `user_id text` required, unique, and a foreign key to `users.id`; `app_fee_active boolean` and `gym_membership_active boolean` are required and default to `false` |
| `attendance_logs` | `id uuid` primary key, generated by the database; `member_id text` required and a foreign key to `users.id`; `scan_timestamp timestamptz` required and defaults to `now()` |

Each user has zero or one subscription row. Each user can have many attendance rows. Foreign keys use restrictive deletion so deleting a user cannot cascade away subscription or attendance history.

**State transitions**: None. Subscription access is represented by the two independently managed boolean fields.

**API surface**:

| Endpoint | Method | Key inputs | Key outputs | Auth | Key errors |
|---|---|---|---|---|---|
| `/rest/v1/users` | GET | JWT `sub` filter, page range | Own user row | Clerk JWT | 401 unauthenticated, 403 denied |
| `/rest/v1/subscriptions` | GET | JWT `sub` filter, page range | Own subscription row and access flags | Clerk JWT | 401 unauthenticated, 403 denied |
| `/rest/v1/attendance_logs` | GET | JWT `sub` filter, ordered page range | Own attendance rows | Clerk JWT | 401 unauthenticated, 403 denied |
| `/rest/v1/attendance_logs` | POST | `member_id` text | Database generated `id` and `scan_timestamp` | Development Supabase Auth scanner JWT only | 401 unauthenticated, 403 denied, 23503 unknown member |

The mobile app uses Supabase's generated REST interface through the existing Supabase JavaScript client. There is no custom API route in this schema slice. Production attendance writes are outside direct table access and must be performed by trusted verifier code after TOTP and replay checks.

**Value sourcing**:

| Action | Value produced or displayed | Source |
|---|---|---|
| Read user | User identity, role, and creation time | `users` columns, scoped by the verified Clerk JWT `sub` |
| Read subscription | App and gym access flags | `subscriptions` columns, scoped by the verified Clerk JWT `sub` |
| Read attendance | Attendance ID, member ID, and scan time | `attendance_logs` columns, scoped by the verified Clerk JWT `sub` |
| Development scanner insert | Member ID | Scanner request input, checked against the `users` foreign key |
| Development scanner insert | Attendance ID and scan time | Database generated UUID and `now()` defaults |
| Scan eligibility | Whether both access flags are active | `subscriptions.app_fee_active` and `subscriptions.gym_membership_active` |
| Production scan insert | Verified member and accepted scan time | Trusted verifier after TOTP validation, replay prevention, and subscription checks; implementation is a separate follow up |

**Key invariants**:
1. `users.id` stores the Clerk JWT subject as text.
2. Each user has at most one subscription row.
3. Both subscription flags default to inactive and are changed only by trusted backend code.
4. A development scanner insert requires both access flags to be active.
5. A production Clerk token cannot insert attendance directly.
6. The database generates attendance IDs and scan timestamps.
7. Deleting a user cannot cascade delete attendance history.

**Security model**:

1. Enable row level security on all three tables.
2. Authenticated Clerk users can select only rows whose user key matches `auth.jwt()->>'sub'`.
3. Mobile clients receive no insert or update permission on `users` or `subscriptions`. Trusted backend provisioning uses a server side Supabase credential.
4. The development attendance insert policy requires the `Scanner@gmail.com` email claim and a native Supabase Auth issuer. It also checks both access flags through a restricted database helper, without granting scanner clients general subscription table reads.
5. Production Clerk kiosk tokens have no direct attendance insert permission. Trusted verifier code validates TOTP, prevents replay, checks both subscriptions, and writes accepted attendance.
6. Never bundle a Supabase service role credential or kiosk password in the app. The public Supabase key is not an authorization boundary; row level security is.

**Configuration required**:
1. `EXPO_PUBLIC_SUPABASE_URL`: Supabase project or local development URL.
2. `EXPO_PUBLIC_SUPABASE_ANON_KEY`: public Supabase key used by the mobile client.
3. Clerk's Supabase integration: configured as a trusted third party JWT issuer in the Supabase project.
4. A Supabase Auth scanner account in local development only. Do not provision this account in the production project.
5. A server side Supabase service role credential for trusted provisioning and production verifier writes. Store it only in the trusted server environment.

**Critical test scenarios**:
1. Happy path: a Clerk member reads its own profile, subscription, and attendance rows, verifies **AC-2**.
2. Failure case: a development scanner insert is rejected when either access flag is false, verifies **AC-4**.
3. Auth and permission: a Clerk kiosk token cannot directly insert attendance, and a member cannot read another member's rows, verifies **AC-5** and **AC-7**.
4. Data integrity: duplicate subscriptions for one user and deletion of a user with attendance rows are rejected, verifies **AC-1** and **AC-6**.

## Build plan

1. Create one Supabase migration for the three tables, constraints, indexes, grants, row level security policies, and the restricted subscription check helper, satisfies **AC-1**, **AC-2**, **AC-3**, **AC-4**, **AC-5**, **AC-6**, and **AC-7**.
2. Configure the mobile Supabase client to use the existing SDK and Clerk session JWT, with only the public URL and key in the app environment, satisfies **AC-2** and **AC-3**.
3. Apply the migration to the local Supabase database and test owned reads, scanner eligibility, denied production direct inserts, unique subscription rows, and restrictive foreign keys, satisfies **AC-1** through **AC-7**.

## Consequences

**Positive**:
1. Clerk identity remains the source of member ownership without a second UUID mapping.
2. Database policies protect member reads and development scanner inserts.
3. Production scan verification cannot be bypassed with a direct Clerk client insert.

**Negative and tradeoffs**:
1. Trusted server code must provision users and subscriptions and perform production attendance writes.
2. The development scanner account must remain isolated from production.
3. RLS policies and a restricted helper need local database tests, not only TypeScript checks.

**Neutral**:
1. The Supabase JavaScript dependency is already present, so this decision does not require another package.
2. The schema does not store TOTP secrets, token replay records, or subscription expiration dates.

## Follow-up

1. Implement trusted Clerk user provisioning with idempotent handling before relying on automatic profile creation.
2. Design and build the production TOTP verifier and replay protection before enabling real kiosk attendance writes.
3. Keep development scanner credentials and production verifier credentials out of the mobile bundle and source control.
